Outline Rendering: UniVRM vs. bevy_vrm1

UniVRM (MToon) Outline Technique

Inverted Hull Method: UniVRM’s MToon shader renders toon-style outlines using a second pass on each mesh. This uses the “inverted hull” technique ￼: front faces are culled so only backfaces render, each vertex is expanded outward along its normal, and the mesh is drawn in the outline color. This creates an outline around the object’s silhouette. Importantly, UniVRM’s outline pass is not a full screen post-process but part of the material’s shader. It does not rely on screen-space edge detection; instead it’s handled per-object in the GPU pipeline.

Depth Testing & Polygon Offset: UniVRM carefully configures depth testing to ensure outlines only appear at the outer silhouette and not over inner surfaces. In the original Unity MToon shader, the outline pass uses a standard depth test (ZTest LEqual in Unity terms) combined with a polygon offset (Offset 1,1) ￼. The polygon offset biases the outline geometry slightly deeper into the scene so that it doesn’t Z-fight with the base mesh and is treated as “behind” the actual surface ￼. This means an outline pixel will only draw if it’s behind the existing geometry in the depth buffer. As a result, interior or back-facing parts of a thin double-sided mesh are typically masked out by depth: the base mesh’s front side already occupied those pixels, so the outline for those backfaces fails the depth test and doesn’t render.

Silhouette-Only Width Scaling: Additionally, MToon dynamically scales outline thickness based on the view angle of the surface. Surfaces directly facing the camera get little or no outline, while true silhouette edges (where the surface is perpendicular to the view) get the full outline width. In Unity’s implementation this is done by multiplying the outline width by a factor like saturate(1 - abs(normalize(viewNormal).z)) ￼. This factor is near 0 for faces head-on to the camera (so no outline is drawn on front-facing polygons) and 1 for faces at a 90° angle (silhouette edges) ￼. This technique effectively suppresses outlines on interior surfaces that are visible through thin double-sided geometry (since those interior faces are usually facing the viewer), limiting the outline to the outer contour.

No Evidence of Stencil Masking: UniVRM’s standard approach does not appear to use an explicit stencil mask for outlines. Instead, it relies on the depth buffer and the above depth bias/angle tricks to confine outlines to the silhouette. There’s also no indication that UniVRM uses any screen-space postprocessing for outlines – it’s all done in the material passes. However, MToon does provide an outline masking texture feature: creators can supply a grayscale mask to disable outlines in certain areas of the model ￼. This is useful for preventing unwanted outlines (for example, on specific parts like hair strands or thin details) and is an artist-controlled form of masking. But by default, the depth-test and culling setup is sufficient to avoid outlines on internal polygons in most cases.

Double-Sided vs. Culling: In UniVRM/Unity, the main material pass honors the material’s culling setting. If a VRM material is marked double-sided, the shader will set Cull Off (no culling) so that both sides of each triangle are drawn ￼. The outline pass, however, still specifically culls front faces (using Cull Front) so that only backfaces contribute to the outline ￼. This combination means the base mesh draws both sides (so interior surfaces are visible and also write to depth), while the outline pass always targets backfaces of the geometry (ensuring outlines come from the “reverse” side of each polygon). UniVRM does not need to dynamically toggle depth-writing – even for double-sided materials, the base pass writes to the depth buffer for all faces as usual. The key is that the outline pass is configured to respect that depth. (Unity’s MToon uses ZWrite On for outlines, same as the base, so outlines also update depth – though the depth bias and tests ensure they usually lie just behind the visible surface.)

bevy_vrm1 Outline Implementation

The bevy_vrm1 plugin also implements an inverted-hull outline, but its configuration differs from UniVRM’s, leading to the issue with magenta-filled interiors. In the current bevy_vrm1 outline pipeline (for MToon materials), front-face culling is enabled and vertices are extruded along normals similar to MToon ￼. However, depth testing in bevy_vrm1’s outline pass was initially set to CompareFunction::Greater with no depth bias ￼ ￼. This meant the outline pixel would draw only if its depth value was greater (farther) than the depth already in the buffer. In theory, that should limit outlines to regions outside the base mesh silhouette. But without any depth bias or additional handling, this approach is fragile for very thin geometry. In practice, the outline and the base surface can end up with nearly the same depth for back-to-back faces, so some “interior” outline fragments erroneously pass the depth test and render on top of the interior surface. Essentially, bevy_vrm1’s outlines were not sufficiently pushed behind the base mesh, allowing backface outlines to appear through thin parts.

Crucially, when a mesh is double-sided (like a piece of cloth with no thickness), the “inside” face of the cloth is just the backside of the outside polygon. In bevy_vrm1, if you look into a sleeve or inside a skirt, those interior faces are drawn by the base pass (since cull is None) and should cover any outline. But due to the minimal depth separation, the outline pass may treat the interior backside as just behind an empty pixel and draw it. The result was the interior of thin cloth appearing solid magenta (the outline color) instead of being properly hidden ￼. This indicates that bevy_vrm1 was failing to mask out outlines on interior backfaces, likely because the depth comparison alone (without bias) wasn’t strict enough in this reverse-Z context or because the outline geometry wasn’t offset behind the front geometry.

Base Pass Depth Writing: There was some question whether bevy_vrm1’s base pass failed to write depth for double-sided meshes. In our investigation, that does not seem to be the core issue – as long as double_sided=true and cull_mode=None are set on the material (which the Elmer.vrm materials have), the base pass in Bevy will render both faces and write their depths correctly. (Notably, older versions of Bevy had a bug where double_sided did nothing without a corresponding cull mode change ￼, but in current usage bevy_vrm1 explicitly sets cull_mode=None for double-sided VRM materials, so backfaces are indeed drawn in the base pass.) The interiors look correct when the outline is disabled, confirming the base geometry and depth buffer are fine. The problem is that the outline pass in bevy_vrm1 doesn’t fully respect the depth of those interior surfaces, due to lacking the adjustments UniVRM makes. Essentially, bevy_vrm1’s outline was drawing in areas it should have been occluded.

Why UniVRM Succeeds (Silhouette Only) vs. Bevy’s Magenta Interiors

To summarize the difference: UniVRM’s outline implementation ensures that only the outer silhouette edges get an outline, whereas bevy_vrm1’s current implementation lets outline pixels bleed into interior regions of thin geometry. UniVRM achieves the correct result by:
	•	Using a depth bias (polygon offset) so outline triangles are rendered slightly behind the base surface ￼. This prevents outlines from z-fighting or appearing on top of front faces.
	•	Using the view-angle factor to essentially zero out outline expansion on faces that face the camera ￼. So if you directly see a surface (like the inside of a sleeve), the outline geometry for that surface is shrunk to nothing or extremely thin. The outline only becomes substantial at glancing angles where a true contour exists.
	•	Relying on normal depth testing (LEqual) so that any outline fragment that is not actually behind the existing geometry will fail the depth test and not draw ￼.

In contrast, bevy_vrm1 was initially using a depth comparison (Greater) without any depth bias, and it did not incorporate the view-angle scaling until recently. This meant the outline geometry for interior backfaces could end up being considered “behind” simply due to precision or lack of offset, and thus passed the depth test to draw over the interior. The result is the magenta fill on internal surfaces: essentially the outline of the backside of a cloth is being drawn even though that backside is directly visible (and should be considered front-facing from the camera’s perspective).

Another way to look at it: in UniVRM, the interior faces either don’t get outlined at all (outline width ≈ 0 for those angles) or the outline gets completely occluded by the front face due to the depth offset. In bevy_vrm1, the outline geometry was not sufficiently occluded or suppressed, so it drew where it shouldn’t. There’s no evidence that UniVRM uses a stencil to achieve this, but it effectively accomplishes the same goal by clever use of depth and geometry adjustments.

Improvements for bevy_vrm1 (Matching UniVRM’s Behavior)

To fix the issue and align bevy_vrm1’s behavior with UniVRM, several changes are recommended:
	•	Implement Depth Bias (Polygon Offset): Adjust the outline pass to push it behind the base surface in depth. Unity’s MToon uses Offset 1,1, and a comparable tweak in Bevy would be to use WGPU’s depth bias in the render pipeline. This was attempted (with careful consideration for Bevy’s reverse-Z depth) ￼ ￼. The idea is to bias the outline fragments so they only draw if genuinely behind the base geometry. Fine-tuning the DepthBiasState (constant and slope factors) or using a slight negative clip-space offset can mimic Unity’s polygon offset. This helps prevent outlines from appearing when a base fragment is at the same depth.
	•	Use View-Dependent Outline Scaling: Incorporate the same edge-angle attenuation that MToon uses. In practice, this means modifying the vertex (or fragment) shader so that when a polygon’s normal is facing toward or away from the camera (|N·V| is high), the outline extrusion amount is reduced. bevy_vrm1 has already explored this: for example, multiplying the outline width by 1.0 - abs(dot(view_dir, normal)) ￼ will make outlines thinner on surfaces seen head-on. A more aggressive approach (e.g. using a power or threshold) could completely eliminate outline on <30° view angles ￼. This ensures interior faces of a thin cloth (which the camera sees nearly head-on) produce little to no outline, matching UniVRM’s silhouette-only effect.
	•	Stencil Masking (if necessary): If depth bias and angle scaling alone are not sufficient, a stencil-buffer approach could be adopted for a robust solution. This would involve writing a stencil value for all pixels drawn in the base pass, and then configuring the outline pass to only draw on pixels where the stencil is not set (i.e. regions not covered by the base mesh) ￼. In effect, this explicitly forbids outline pixels from overwriting any pixel already occupied by the main geometry. UniVRM does not appear to use this method by default, but it’s a sure-fire fix for the problem and could be implemented in bevy_vrm1 given access to a depth-stencil buffer. (One must ensure Bevy’s renderer provides a stencil attachment and set up the compare ops accordingly ￼.)
	•	Correct Depth Compare Mode: It may be worth aligning the depth test mode with Unity’s. UniVRM uses LessEqual (meaning an outline will draw even if it exactly equals the depth of an existing pixel, typically safe with the depth bias). bevy_vrm1 was using Greater and later tried GreaterEqual ￼ ￼. The exact setting should be tuned along with depth bias – for example, using GreaterEqual with a slight depth push ensures outlines don’t vanish due to precision (allowing equality covers the case where outline depth == base depth after bias). The combination of GreaterEqual + depth bias in Bevy’s reverse-Z context is analogous to LEqual + offset in Unity. This should be tested to find the optimal configuration that yields silhouette outlines without leaks.
	•	Respect Material Cull Settings: Ensure that the base pass for double-sided materials continues to disable backface culling (which appears to be handled via cull_mode=None). This way, all interior faces are drawn in the base pass and populate the depth buffer. That is already the case in bevy_vrm1 (Elmer.vrm’s clothing had double_sided=true and was set to cull none). Maintaining this is important so that the depth buffer knows about interior surfaces. (In summary, keep base pass culling in sync with UniVRM: UniVRM sets Cull Off for double-sided ￼, and bevy_vrm1 should do the same.)
	•	Outline Width Mask: Although not strictly part of the rendering algorithm, supporting the outline mask texture from the VRM/MToon material could help creators fine-tune where outlines appear. UniVRM’s MToon allows a mask image to turn off outlines on specific areas ￼. If bevy_vrm1 honors this texture, it could automatically eliminate outlines on parts of the model that were never intended to have them (this might include some thin interior parts if the modeler painted the mask accordingly). This is a secondary improvement, but it would bring bevy_vrm1 closer to feature parity with UniVRM.

In conclusion, the discrepancy comes down to depth and culling handling in the outline pass. UniVRM avoids drawing interior outlines by using depth-biasing and orientation-based suppression, whereas bevy_vrm1’s current outline pipeline lacked those safeguards, causing backfaces of thin double-sided meshes to render as outlines (the magenta interior issue). By adopting the above improvements – essentially mirroring UniVRM’s outline rendering technique – bevy_vrm1 can achieve correct outline behavior where only the outer silhouette of the model is outlined. This means implementing the same stencil/depth tricks or their equivalents so that, just like UniVRM, outlines are only visible at the character’s silhouette and never fill in the inside of thin geometry ￼ ￼. With these changes, bevy_vrm1’s output should match UniVRM’s, eliminating the unwanted magenta interior artifacts.
